OOP vs Procedural Programming

Up to this point, most of the programming we have done has been procedural programming.

What is procedural programming?

Procedural programming organizes a program as:

  • data stored in variables (numbers, strings, lists, dictionaries, etc.)
  • procedures (functions) that take that data as input and produce output

A typical procedural workflow looks like:

  • create variables
  • pass them into functions
  • get results back
  • store results in new variables

In procedural code, the structure of the program is mainly:

  • the sequence of steps you write, and
  • the functions you call in that sequence.

What changes with OOP?

Object-Oriented Programming organizes a program around objects, where:

  • the data and the operations on that data are grouped together

Instead of keeping data in separate variables and passing them into functions, we bundle them into a class and create objects from it.

Quick comparison

Procedural Programming:

  • Data and functions are usually separate.
  • Functions often require many parameters.
  • The program reads like a list of steps.

OOP:

  • Data + behaviour are packaged together.
  • Methods operate on an object’s own stored data.
  • The program reads like interactions between objects.

Why learn OOP?

  • OOP is most helpful when programs get larger and you want to keep related code together, reduce duplicated logic, and make your code easier to extend and maintain.
  • Procedural programming is still extremely useful (and we will keep using it).

Classes

Motivation

So far we have used built-in data types such as:

int, float, str, bool, list, dict, tuple

These data types define their respective data they hold and behaviour (through methods).

Example:

  • str: name = "john" (data),
  • name.capitalize() (behaviour)

But what if we want to represent something more complex, like a

  • Person, Student, or an Employee (identity + roles system)?
  • Sensor, LabSample, and Logger (measurement pipeline system)?
  • AssignmentPosted, ServerDown, NewComment (event-driven notification system)?

Each of these having there own defined data and behaviour?

We do this using classes, one of the core building blocks in Python.

The Main Idea

Classes help you structure programs by bundling together:

  • the data you want to store, and
  • the operations you want to perform on that data

Classes act like a template (or blueprint).

  • From a class, we can create objects (also referred to as instances).
  • Each object follows the same template (definied by its class), but stores its own data.

Remark: We will discuss Objects in more detail below.

Example (high-level)

In an OOP program, you might represent employees using an Employee class.

An Employee class might define the following data:

  • an ID
  • a name
  • a department
  • a desk number

And it might support operations like:

  • requesting time off
  • updating a department
  • calculating pay

Class Building Blocks

A class is made of:

  • attributes (also called fields): the data we want to store
  • behaviour (also called methods): actions the object can perform

The attributes often use types we already know:

  • integers, strings, Booleans, floating-point numbers, lists, etc,
  • and later: other classes

The behaviour (methods) are internal fuctions that can

  • manipulate attributes,
  • send out messages to other objects.

Example: Employee class (revisited)

Attributes (data):

  • id
  • name
  • department
  • desk_number

Behaviour (actions):

  • requesting_time_off()
  • updating_department()
  • calculating_pay()

Objects (instance)

Creating Objects (Instances)

An object is an instance of a given class:

  • Created from a class.
  • Stores its own values for the class attributes.
  • Runs the class methods (behaviour) on its own data.
  • Exist alongside many other objects of the same class (each with different data)

Example: Employee objects (instances)

An instance of the Employee class could be an employee named turing who holds:

  • ID : 12061912
  • name : Alan Turing
  • department: Computer Science
  • desk number: 1

We might have an addition instances of the Employee class named hilbert:

  • ID : 3141592
  • name : David Hilbert
  • department: Mathematics
  • desk number: 271

Each of these instanaces support the operations defined in the Employee class:

  • requesting_time_off()
  • updating_department()
  • calculating_pay()

Class Design

Designing Classes

A well-designed class should have one clear purpose.

If a class tries to do too many unrelated things:

  • it becomes harder to understand,
  • it becomes harder to reuse,
  • and it can lead to messy code where unrelated parts can accidentally interfere with each other.

A simple design rule

If you find yourself saying

this class does X and also Y and also Z…,

then it may be a sign that the class should be split into smaller classes.

A practical checklist

When you are designing (or reviewing) a class, start with its class comment (docstring):

  1. Is the description short and clear?

    • If it takes a long paragraph to explain the class, it may be doing too much.
    • Try breaking the description into a few short sentences.
    • If those sentences describe different jobs, that’s a hint you might need multiple classes.

  2. Do the attributes make sense given the description?

    • Every attribute should fit naturally with the class’s purpose.
    • If an attribute feels out of place, either:
      • the attribute doesn’t belong, or
      • the class purpose is unclear.

  3. Do the behaviours (methods) match the purpose?

    • Look at how the class’s data is used.
    • If methods are doing work that doesn’t match the class description, the class design should be reconsidered.

Key takeaway

A good class:

  • has a short, clear description,
  • contains data that matches that description,
  • and provides behaviour that makes sense for that data.

Class Terminology Summary

Here is a summary of terminology found in OOP:

Class

  • A class defines a bundle of data and behaviour.
  • It acts as a template (blueprint) for creating objects.

Object / Instance

  • An object (or instance) is one specific example created from a class.
  • All objects made from the same class have the same kinds of attributes, but each object stores its own values.
  • Objects of the same class can respond to the same set of operations.

Attribute / Field / Instance Variable

  • Attributes are the pieces of data stored inside an object.
  • The object’s state is the current values of its attributes at a particular moment.

Method

  • A method is a function defined inside a class.
  • Methods describe behaviour that acts on the object’s own data.

Message (request)

  • In OOP, we often describe code as sending a message to an object.
  • This means we are requesting that the object do something or return something.
  • For example: compute a result or update your data.
  • The key idea: the object controls how it carries out that request.

Object Oriented Systems

In many real applications, we are not modeling just one object, we are modeling a system made up of several interacting components.

A useful way to design an OO system is:

  1. Identify the main components (the “things” in the system).
  2. Decide what data each component should store.
  3. Decide what behaviour each component should provide.
  4. Decide how components interact (who talks to who, and what information they exchange).
  5. Keep clear boundaries: each component should have a small, well-defined job.

Example: a simple “lab measurement pipeline”

Imagine a lab workflow with multiple parts:

  • a sensor produces readings
  • a sample stores readings
  • a logger saves results
  • an analyzer summarizes and checks tolerances
  • a lab session coordinates everything

Observations

  • Each component has a small job.
  • LabSession is the coordinator (the glues the pieces together).
  • The program structure is visible in the set of classes and how they interact.

This is the key OO idea: instead of one long script, we build a system out of parts that cooperate.
