The object Class and Inheritance

The Built-in object Class

  • object is the root (base) class of the Python class hierarchy.
  • Every class inherits from it.

What happens if you write:

class Person:

Python treats it (conceptually) like:

class Person(object):

So object is the default base class when you don’t specify one.

# These two class headers are equivalent in Python 3

class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age


class Person(object):
    def __init__(self, name, age):
        self.name = name
        self.age = age

Why this matters

Because every class ultimately inherits from object:

  • Methods defined in object are available for all objects.
  • This gives Python objects a shared set of common behaviours and attributes.

Common special methods inherited from object:

  • __init__ –> object initialization (constructing an instance)
  • __str__ –> readable string form (used by print(...))
  • __eq__ –> equality comparison (==)
  • __hash__ –> hashing (used in sets/dict keys – we will not be covering this topic)

Standard attributes inherited from object:

  • __class__ –> the object’s class
  • __dict__ –> instance attributes stored in a dictionary (if the class allows it)
  • __doc__ –> docstring
  • __module__ –> module name where the class is defined

Subclasses

Why do we make subclasses?

A subclass exists to create a more specific version of a superclass.

  • The superclass holds the shared, generic stuff (common attributes + methods).
  • Each subclass reuses that shared stuff, then adds or refines what makes it special.

If your subclass doesn’t actually use or refine what it inherits, it might be the wrong place in the hierarchy.

What should a subclass do?

A good subclass usually does one or more of these:

1) Extend the public interface

  • Add new attributes or methods that the parent class doesn’t have.
  • Example: Employee adds an id and calculate_pay() beyond Person.

2) Change (override) how inherited behaviour works

  • Replace a parent method with a more specific version in the subclass.
  • Example: SalesPerson might override calculate_pay() (from it’s parent (super) class Employee) to behave differently.

3) Add new behaviour that uses inherited behaviour

  • New methods in the subclass should often call or rely on parent attributes/methods.
  • Example: calculate_pay() grabs self.age (inherited from Person) first, then does subclass-specific movement.
  def calculate_pay(self, hours_worked):
      rate_of_pay = 7.50
      if self.age >= 21:
          rate_of_pay += 2.50
      return hours_worked * rate_of_pay

Example: A Conveyance hierarchy

Imagine a superclass:

Conveyance

  • attributes: doors, fuel (with default values)
  • method: start_up() (starts the engine)

Subclasses:

  • Tank
  • Car
  • Dinghy

How to Judge if the Subclases Tank, Car, and Dinghy are good fits for Conveyance?

Ask yourself: Does it meaningfully refine or reuse what Conveyance provides?

Questions:

  1. Which subclasses feel correct, and why?
  2. Which inherited features does each subclass actually use?

Tank (good fit)

  • Changes an inherited value (e.g., number of doors = 1)
  • Uses inherited behaviour (start_up()) inside another method (e.g., move())
  • Adds its own new attribute(s)

Car (good fit)

  • Changes an inherited value (e.g., number of doors = 4)
  • Uses inherited behaviour (start_up() in it’s accelerate() method)
  • Adds new behaviour that uses inherited data (e.g., accelerate() uses fuel)

Dinghy

  • Adds new attribute sails and method set_sail()
  • But it doesn’t use inherited features like doors, fuel, or start_up()

Question: Dose doors, fuel, and start_up() make sense for a dinghy?

Answer: If a dinghy is a small sail-powered boat with no engine, then no.

Issue at Hand:

  • the superclass Conveyance isn’t too broad, but the class actually models a motor vehicle
  • Dinghy should not inherit from it (or the hierarchy should be redesigned)

Question: If Dinghy doesn’t need an engine, what would you redesign?

Overriding Methods

What does overriding mean?

Overriding happens when:

  • a method is defined in a superclass (e.g., Person), and
  • the subclass (e.g., Employee) defines a method with the same name.

Both objects can respond to the method call, but:

  • Person uses the Person version
  • Employee uses the Employee version

Why override methods?

Because a subclass is more specific.

  • A Person might print: name + age
  • An Employee might print: name + age + employee id

Same method name, but a more detailed version in the subclass.

Example: overriding __str__ Method

Recall: The method __str__ controls what you see when you do print(obj).

  • For an instance of Person, __str__() might return something like:

    "Alan Turing is 54"

  • For an instance of Employee, __str__() might return something like:

    "Margaret Hamilton is 51 (id: 1234)"

class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def __str__(self):
        return self.name + " is " + str(self.age)


class Employee(Person):
    def __init__(self, name, age, id):
        super().__init__(name, age)
        self.id = id

    # overriding Person.__str__
    def __str__(self):
        return self.name + " is " + str(self.age) + " (id: " + str(self.id) + ")"
turing = Person("Alan Turing", 54)
print(turing)  # uses Person.__str__()

hamilton = Employee("Margaret Hamilton", 51, 1234)
print(hamilton)  # uses Employee.__str__()
Output
Alan Turing is 54
Margaret Hamilton is 51 (id: 1234)

How Python Chooses which Method to Run (for Single Inheritance)

When you call a method on an object (like __str__()):

  1. Python looks in the class of the object first (the class used to build it).
  2. If it finds the method there, it uses that one.
  3. If not, Python looks in the parent class.
  4. Then the parent’s parent, and so on …

This search up the family tree is why the subclass version replaces the superclass version for subclass objects.

Remark: For multiple inheritance this search is complicated, and we will discuss in more details later.

Extending Superclass Methods

The Problem with Duplicated Code

In the overriding example, Employee.__str__() repeated the same name and age formatting that already existed in Person.__str__():

class Person:
    ...
    # Person.__str__
    def __str__(self):
        return self.name + " is " + str(self.age)

class Employee(Person):
    ...
    # overriding Person.__str__
    def __str__(self):
        return self.name + " is " + str(self.age) + " (id: " + str(self.id) + ")"

Issue: If we change how Person formats its string later, we’d have to remember to update Employee too

The Solution: call the superclass method, then add more

A subclass can extend a superclass method by:

  1. calling the superclass version using super()
  2. adding subclass-specific information

This is the same idea we use in __init__:

  • run the parent setup first
  • then do the subclass extras
class Employee(Person):
    def __init__(self, name, age, id):
        super().__init__(name, age) # Calling the constructor __init__() from the superclass Person
        self.id = id

Example: extend __str__ without repeating yourself

  • Person.__str__() creates the base string (name + age)
  • Employee.__str__() reuses that string and appends the employee id

Result:

  • only one place in the code converts name + age into a string
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def __str__(self):
        return self.name + " is " + str(self.age)


class Employee(Person):
    def __init__(self, name, age, id):
        super().__init__(name, age)
        self.id = id

    def __str__(self):
        # reuse Person.__str__() and then add Employee-specific details
        return super().__str__() + " (id: " + str(self.id) + ")"
turing = Person("Alan Turing", 54)
print(turing)  # uses Person.__str__

hamilton = Employee("Margaret Hamilton", 51, 1234)
print(hamilton)  # uses Employee.__str__
Output
Alan Turing is 54
Margaret Hamilton is 51 (id: 1234)

Summary

  • Override when you want different behaviour.
  • Extend when you want the same behaviour plus more, and you don’t want to copy/paste.

Inheritance-Oriented Naming Conventions

Protected and Private Conventions

Python doesn’t have true access modifiers like public / protected / private (unlike Jave, C#, C++).

Instead, it uses naming conventions that communicate intent.

There are two common conventions to know when inheritance is involved:

1) Single underscore: _name (protected by convention)

  • A name starting with one underscore is a signal:
    • This is an internal detail — please don’t use it from outside the class.
  • In practice:
    • it’s still accessible (Python won’t stop you)
    • subclasses are allowed to use it when needed

So you can think of _something as:

  • publicly accessible, but meant for internal use (including subclasses)

2) Double underscore: __name (private via name mangling)

  • A name starting with two underscores is meant to be class-private.
  • It is intended not to be used from outside the class — including subclasses.

Python supports this idea using name mangling:

  • __somename inside class Person becomes (roughly): _Person__somename

This makes accidental access harder and reduces name clashes in subclasses.

Important details:

  • The mangling rule applies to names with:
    • at least two leading underscores
    • and at most one trailing underscore
  • Example:
    • __x gets mangled
    • __x__ usually does NOT get mangled in the same way (often used for dunder (special) methods)
class Person:
    def __init__(self, name, age):
        self.name = name
        self._age = age          # "protected by convention"
        self.__secret = "this is a secret"    # "private" via name mangling

    def reveal(self):
        # Inside the class, both are accessible normally
        return self._age, self.__secret
p = Person("Alan Turing", 54)
print(p.reveal())
Output
(54, 'this is a secret')
class Employee(Person):
    def __init__(self, name, age, id):
        super().__init__(name, age)
        self.id = id

    def show(self):
        # Subclasses can access _age (convention says this is OK)
        print("Age:", self._age)

        # This will fail because __secret is mangled to _Person__secret
        print(self.__secret)  # AttributeError
        #print(self._Person__secret) # Works
e = Employee("Margaret Hamilton", 51, 1234)
e.show()
Output
Age: 51
---------------------------------------------------------------------------

      1 e = Employee("Margaret Hamilton", 51, 1234)
----> 2 e.show()

Summmary:

Useage:

  • _attribute when it’s an internal detail but subclasses may reasonably reuse it.
  • __attribute when you want to strongly discourage subclass access.

Remember: Python conventions are about communication and design discipline, not absolute enforcement.

Polymorphism (An Introduction)

What is polymorphism?

Polymorphism is the idea that you can call the same method name on different objects, and each object will do the right thing for its own class.

  • The message (method call) is the same.
  • The behavior can differ depending on the object’s class.

Polymorphism: “Ask different kinds of things to do the same action.”

Example 1: An Informal Contract

Consider the function:

def night_out(entity):
    entity.eat()
    entity.drink()
    entity.sleep()

This function doesn’t care what entity is. It only cares that entity can respond to:

  • eat()
  • drink()
  • sleep()

Any object that supports those methods can be passed in.

class Person:
    def eat(self):
        print("Person - Eat")

    def drink(self):
        print("Person - Drink")

    def sleep(self):
        print("Person - Sleep")


class Employee(Person):
    # Overrides all three methods
    def eat(self): 
        print("Employee - Eat")

    def drink(self):
        print("Employee - Drink")

    def sleep(self):
        print("Employee - Sleep")

class Dog:
    # Not related by inheritance, but still works
    # Note: This is type of Polymorphism is related to an important concept in
    # Python called Duck Typing (discussed in more detail later)
    def eat(self):
        print("Dog - Eat")

    def drink(self):
        print("Dog - Drink")

    def sleep(self):
        print("Dog - Sleep")
def night_out(entity):
    entity.eat()
    entity.drink()
    entity.sleep()

# All of these objects work with the night_out() function
print("-" * 20)
night_out(Person())

print("-" * 20)
night_out(Employee())

print("-" * 20)
night_out(Dog())
Output
--------------------
Person - Eat
Person - Drink
Person - Sleep
--------------------
Employee - Eat
Employee - Drink
Employee - Sleep
--------------------
Dog - Eat
Dog - Drink
Dog - Sleep

Why it’s useful

As the programmer, you don’t have to care how the object does the job - only that it can do the job.

So instead of writing separate functions for each type, you write one function that works for anything that supports the needed methods (behaviour).

Summary

Polymorphism lets you write code that is:

  • more reusable
  • easier to extend
  • less full of type-checking and special cases

Looking Ahead

Polymorphism naturally leads to:

  • Duck typing
  • Informal contracts
  • Protocols

These are all topics that we will cover later on in this course
