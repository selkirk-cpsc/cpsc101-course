Compile-Time vs Run-Time Errors

From C to Python

Errors

Python is an interpreted language, which differs from compiled languages (like C).

This difference changes how and when errors are handled.

From the point of view of a compiled language (like C), there are two main stages where errors can occur:

  • Compile-time errors: the compiler refuses to build the program.
  • Run-time errors: the program builds successfully, starts running, and then fails during execution.

Python changes when errors are discovered.

Errors from a C Perspective

Compile-Time Errors

In C, the compiler checks many expectations before the program runs:

  • syntax must be valid
  • types must match function signatures (to a degree)
  • names must be declared
  • code must be structurally well-formed

If expectations fail here, the program never runs.

Run-Time Errors

In C, even a program that compiles can still fail at runtime:

  • dividing by zero
  • accessing invalid memory
  • file not found
  • reading bad input

These failures happen only when that code path is executed.

Errors from a Python Perspective

Python does have a compilation step (to bytecode), but in practice:

Python does most checking at runtime.

So many mistakes that would be caught early in C show up as exceptions while the program runs.

Three Error Types

In Python, the big divide you will experience is:

  • Syntax errors → the program won’t start (similar to compile-time failure)
  • Exceptions → the program started, but an expectation was violated at runtime
  • Logic errors → the program runs and produces the wrong result (no exception)
# SyntaxError (program won't start)
if True
    print("missing colon")
Output
  Cell In[2], line 2
    if True
           ^
SyntaxError: expected ':'

# Runtime exception (program starts, fails when executed)
x = 0
print(10 / x)   # ZeroDivisionErrorc
Output
---------------------------------------------------------------------------
ZeroDivisionError                         Traceback (most recent call last)
Cell In[3], line 3
      1 # Runtime exception (program starts, fails when executed)
      2 x = 0
----> 3 print(10 / x)   # ZeroDivisionErrorc

ZeroDivisionError: division by zero
# Logic error (runs, but wrong result)
def average(a, b):
    return a + b / 2   # wrong precedence

print(average(4, 6))   # no exception, wrong answer
# Ouput should be 5 ((4+6)/2 = 10/2 = 5)
Output
7.0

Question: How does Python manage each of the three errors above differently?

Key Takeaway

  • C catches many problems before the program runs (compile-time).
  • Python catches many problems during execution (run-time exceptions).

For the remainder of this lecture, we will focus on run-time errors and how Python manages them through exceptions.

Runtime Errors

Runtime Errors

Python manages runtime errors through exceptions:

  • The program encounters an operation it cannot complete
  • Python stops execution
  • An exception is raised

Lets take a look at a few different runtime errors:

TypeError

  1. You try to perform an operation on two types that don’t match:
3 + "hello" # Can't add an interger and a string
Output
---------------------------------------------------------------------------
TypeError                                 Traceback (most recent call last)
Cell In[5], line 1
----> 1 3 + "hello" # Can't add an interger and a string

TypeError: unsupported operand type(s) for +: 'int' and 'str'
  1. Wrong callable behavior:
def process(x):
    x()

process(10)
Output
---------------------------------------------------------------------------
TypeError                                 Traceback (most recent call last)
Cell In[6], line 4
      1 def process(x):
      2     x()
----> 4 process(10)

Cell In[6], line 2, in process(x)
      1 def process(x):
----> 2     x()

TypeError: 'int' object is not callable

Remarks:

  • The objects exist, but do not support the expected interface.
    • You can’t add a string to an integer: 3 + "hello"
    • Integers aren’t callable (functions are callable): 10()
  • An interface describes the set of operations (methods or behaviors) an object is expected to support.
  • Python discovers these issues only at run time.

AttributeError

You try calling a method on an object that doesn’t exist:

def night_out(x):
    x.eat()
    x.drink()

night_out(42)
Output
---------------------------------------------------------------------------
AttributeError                            Traceback (most recent call last)
Cell In[7], line 5
      2     x.eat()
      3     x.drink()
----> 5 night_out(42)

Cell In[7], line 2, in night_out(x)
      1 def night_out(x):
----> 2     x.eat()
      3     x.drink()

AttributeError: 'int' object has no attribute 'eat'

Remarks:

  • Python does not care about the object’s type
  • It only cares whether the object has the required methods

ValueError: Correct Type, Wrong Meaning

You try to pass an argument to a function that is outside its valid domain:

import math
math.sqrt(-10)
Output
---------------------------------------------------------------------------
ValueError                                Traceback (most recent call last)
Cell In[8], line 2
      1 import math
----> 2 math.sqrt(-10)

ValueError: math domain error

Remarks:

  • You passed sqrt() the correct type (-10 is a numerical value)
  • But its meaning (a negative number) is incorrect: sqrt(-10) is not defined over the real numbers

NameError: Using a Name That Does Not Exist

A NameError occurs when Python encounters a variable or function name that has not been defined.

x = 2
sqrt(x)
Output
---------------------------------------------------------------------------
NameError                                 Traceback (most recent call last)
Cell In[9], line 2
      1 x = 2
----> 2 sqrt(x)

NameError: name 'sqrt' is not defined

Remarks:

  • Python looks up names at run time, not ahead of execution.
  • The program is syntactically correct, but the name does not exist in the current scope.
  • This reinforces that Python executes code top to bottom, resolving names as it goes.

Observations & Notes

  • Each of the examples above produces an error message called a traceback.
  • A traceback shows where an error occurred and what went wrong.
  • The mechanism Python uses to signal and communicate these errors is called an exception.

Tracebacks

What is a Traceback?

A traceback is a report containing:

  • the exception type (what kind of contract was violated)
  • the exception message (extra context)
  • the call stack (which functions were active)
  • file names + line numbers (where to look)

It is a debugging tool, not just an error message.

Example

Consider the script that is contained in the file main.py:

# main.py
def g(x):
    return 10 / x

def f(x):
    return g(x)

def main():
    return f(0)

main()

Running this script produces the follow output:

Traceback (most recent call last):
  File "/home/ryan/git/cpsc101/lectures/lecture05/main.py", line 10, in <module>
    main()
  File "/home/ryan/git/cpsc101/lectures/lecture05/main.py", line 8, in main
    return f(0)
           ^^^^
  File "/home/ryan/git/cpsc101/lectures/lecture05/main.py", line 5, in f
    return g(x)
           ^^^^
  File "/home/ryan/git/cpsc101/lectures/lecture05/main.py", line 2, in g
    return 10 / x
           ~~~^~~
ZeroDivisionError: division by zero

Step 1: Read the Bottom Line First

Bottom line:

  • Exception type: ZeroDivisionError
  • Message: division by zero

Meaning: An arithmetic expectation was violated: the divisor must not be zero.

Step 2: Find Where the Exception Was Raised

Look for the last stack frame pointing to your code (closest to the bottom):

File “…/main.py”, line 2, in g return 10 / x

This is where Python raised the exception:

  • the operation 10 / x was attempted
  • at runtime, x was 0
  • Python stopped and raised ZeroDivisionError

Step 3: Follow the Call Chain (How We Got There)

Now read from the top downward to see the path:

  1. main() was called (line 10)
  2. main() calls f(0) (line 8)
  3. f(x) calls g(x) (line 5)
  4. g(x) tries 10 / x (line 2) –> exception raised

So the “story” is:

main –> f(0) –> g(0) –> 10 / 0 –> ZeroDivisionError

What Tracebacks Usually Tell You

A traceback can usually help you decide:

  1. Is this a Type problem?

    • TypeError, AttributeError

  2. Is this a Value problem?

    • ValueError, ZeroDivisionError

  3. Is this a Name / scope problem?

    • NameError

  4. Is this a missing method/attribute problem?

    • AttributeError (important for duck typing - disscused later)

Practical Habits

When you get a traceback:

  • Do not panic
  • Do not start changing random lines
  • Read the last line (exception type + message)
  • Then find the first relevant line in your code
  • Fix the expectation mismatch, not the symptom

Exceptions

What Is an Exception?

(An Object View Point)

In Python, everything is an object:

  • integers
  • strings
  • functions
  • class instances
  • exceptions

An exception is not a special language feature. It is an object used to communicate a problem at runtime.

Initialize the ValueError Exception Class

Below, we create an exception object from the ValueError class and inspect:

  • its type
  • its message
  • its attributes
  • and how Python stores traceback and chaining information
# Inspecting the ValueError *class*
print("Inspecting the ValueError class:")
print('-'*40)
print("class name       =", ValueError.__name__)
print("base classes     =", [cls.__name__ for cls in ValueError.__mro__])
print("docstring        =", ValueError.__doc__)

print()
# Create an exception object directly (no errors needed)
err = ValueError("Age must be between 0 and 120")
print("Inspecting an instances of ValueError class (err):")
print('-'*40)
print("type(err)         =", type(err))          # Class ValueError
print("str(err)          =", str(err))           # human-friendly message
print("repr(err)         =", repr(err))          # detailed representation for debugging
print("args.e            =", err.args)
print("err.__traceback__ =", err.__traceback__)  # None here (no exception was raised)
Output
Inspecting the ValueError class:
----------------------------------------
class name       = ValueError
base classes     = ['ValueError', 'Exception', 'BaseException', 'object']
docstring        = Inappropriate argument value (of correct type).

Inspecting an instances of ValueError class (err):
----------------------------------------
type(err)         = <class 'ValueError'>
str(err)          = Age must be between 0 and 120
repr(err)         = ValueError('Age must be between 0 and 120')
args.e            = ('Age must be between 0 and 120',)
err.__traceback__ = None

Remarks:

  • The message you see comes from str(e).
  • e.args stores the data passed into the exception.
  • No traceback is attached unless the exception is actually raised.

Exception Class Hierarchy

Python organizes exceptions into a class hierarchy:

Each exception type represents a category of failure, such as:

  • invalid operations
  • invalid values
  • missing attributes

This allows Python (and you) to:

  • distinguish what went wrong
  • decide what can be handled

Note: You do not need to memorize this hierarchy.

What matters is:

  • Different kinds of expectation failures produce different exception types
  • The exception type tells you what kind of contract was violated

Exceptions as Messages

From a design perspective, an exception is a message (signal) that something has gone wrong at runtime.

It is Python’s way of saying:

  • “This operation cannot be completed”
  • “This object does not meet the required expectations”
  • “The contract was violated”

Exceptions are signals, not crashes or bugs.

Raising an Exception

When Python detects a violation of expectations, it raises an exception.

Raising means:

  • an exception object is created
  • normal execution stops
  • control must move elsewhere

Think of raising as:

“I cannot continue — someone else must decide what to do.”

x = 0 # Python executes this statement
result = 10/x # Python raises this automatically
print(result) # print(result) never executes
Output
---------------------------------------------------------------------------
ZeroDivisionError                         Traceback (most recent call last)
Cell In[11], line 2
      1 x = 0 # Python executes this statement
----> 2 result = 10/x # Python raises this automatically
      3 print(result) # print(result) never executes

ZeroDivisionError: division by zero

Person Class Revisited

Example: Person Class Revisited

# Person class from last week
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def __str__(self):
        return self.name + " is " + self.age
turing = Person() # raise a TypeError exception
Output
---------------------------------------------------------------------------
TypeError                                 Traceback (most recent call last)
Cell In[13], line 1
----> 1 turing = Person() # raise a TypeError exception

TypeError: Person.__init__() missing 2 required positional arguments: 'name' and 'age'
# Fix
turing = Person("Alan Turing", 51)
print(turing) # raises another Type Error exception
Output
---------------------------------------------------------------------------
TypeError                                 Traceback (most recent call last)
Cell In[15], line 1
----> 1 print(turing) # raises another Type Error exception

Cell In[12], line 8, in Person.__str__(self)
      7 def __str__(self):
----> 8     return self.name + " is " + self.age

TypeError: can only concatenate str (not "int") to str

From the traceback, we see that the TypeError is pointing to an issue with the __str__ method inside the Person

Cell In[19], line 8
      7 def __str__(self):
----> 8     return self.name + " is " + self.age

This error is then propagated upward to the call statement:

Cell In[22], line 1
----> 1 print(turing) # raises another Type Error exception

Cell In[19], line 8
      7 def __str__(self):
----> 8     return self.name + " is " + self.age

TypeError: can only concatenate str (not "int") to str
# Fix
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def __str__(self):
        #return self.name + " is " + self.age # Throws a TypeError exception
        return self.name + " is " + str(self.age) # fix: type cast self.age to a string
turing = Person("Alan Turing", 51)
print(turing)
Output
Alan Turing is 51

Sumamry

When an exception is raised:

  1. Python stops normal execution
  2. The exception is propagated upward
  3. If nothing handles it, Python reports:
    • the type of exception
    • where it occurred

---------------------------------------------------------------------------

Cell In[22], line 1
----> 1 print(turing) # raises another Type Error exception

      7 def __str__(self):
----> 8     return self.name + " is " + self.age

This is Python saying:

“I cannot continue under these conditions.”*
