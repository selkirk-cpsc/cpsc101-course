Custom Exceptions

Motivation

So far, we have been dealing with built-in exceptions such as:

  • ValueError (correct type, wrong meaning)
  • TypeError (wrong operation / wrong interface)
  • ZeroDivisionError (invalid math operation)
  • NameError (name does not exist)

Sometimes, these names are too generic.

Example:

  • Suppose your program has a rule: ages must be between 0 and 120
  • You could raise a ValueError
  • But the name ValueError does not clearly communicate what the problem means in your program

Python allows you to define custom exceptions to represent specific kinds of contract violations.

Creating Your Own Exceptions

You can create a custom exceptions by creating a subclass of Exception:

class CustomException(Exception)
    ...

This allows you to:

  • give the error (contract violation) a meaningful name (e.g., InvalidAgeException),
  • attach context (e.g., the invalid value), and
  • write a clear, human-readable message

As an example lets build a custom exception, InvalidAgeException, and use it inside a Person class to enforce the rule:

ages must be between 0 and 120

class InvalidAgeException(Exception):
    """Valid ages must be between 0 and 120"""

This exception represents one specific idea:

“An age value was provided that violates the rules of a Person.”

Instead of saying:

  • “something went wrong”

We can now say:

  • “the age is invalid”

Using the Exception in a Class

We now enforce the contract inside the class Person.

If the contract is violated (Valid ages must be between 0 and 120):

  • the class raises the exception InvalidAgeException,
  • then responsibility moves to the caller
class Person:
    def __init__(self, name, age):
        if not (0 <= age <= 120):
            raise InvalidAgeException("Valid ages must be between 0 and 120")

        self.name = name
        self.age = age

    def __str__(self):
        return f"Person[{self.name}] is {self.age}"
turing = Person("Alan Turing", -10)

In the Person class, if that expectation is violated:

  • the exception InvalidAgeException is raised immediately within the constructor method,
  • thus forcing the object to never be initalised

Handling Custom Exceptions

Handling Custom Exceptions

Code that uses Person can now respond explicitly to this kind of failure.

try:
    turing = Person("Alan Turing", -1)
except InvalidAgeException:
    print("An invalid age was provided.")
Output
An invalid age was provided.

Adding Context to the Exception

Sometimes, we want to know:

  • what value caused the failure

We can store that information inside the exception object.

class InvalidAgeException(Exception):
    """Valid ages must be between 0 and 120"""

    def __init__(self, value):
        self.value = value

    def __str__(self):
        return f"InvalidAgeException({self.value}): {self.__doc__}"
class Person:
    def __init__(self, name, age):
        if not (0 <= age <= 120):
            raise InvalidAgeException(age)

        self.name = name
        self.age = age
try:
    turing = Person("Alan Turing", -1)
except InvalidAgeException as e:
    print(e)
Output
InvalidAgeException(-1): Valid ages must be between 0 and 120

Exception Chaining

Motivation

So far we are assuming the age (in our Person class) has already been provided as an integer.

But what if the age comes from user input?

Example: age_text = "twelve"

Now we have two different failure cases:

  1. the text cannot be converted to an integer (ValueError)
  2. the value converts, but violates our range rule (InvalidAgeException)
class Person:
    def __init__(self, name, age_text):
        age = int(age_text) # Might raise ValueError
        
        if not (0 <= age <= 120):
            raise InvalidAgeException(age)

        self.name = name
        self.age = age
turing = Person("Alan Turing", "thirty one")
Output
---------------------------------------------------------------------------
ValueError                                Traceback (most recent call last)
Cell In[10], line 1
----> 1 turing = Person("Alan Turing", "thirty one")

Cell In[9], line 3, in Person.__init__(self, name, age_text)
      2 def __init__(self, name, age_text):
----> 3     age = int(age_text) # Might raise ValueError
      5     if not (0 <= age <= 120):
      6         raise InvalidAgeException(age)

ValueError: invalid literal for int() with base 10: 'thirty one'

Observation

If int(age_text) fails, we could let Python raise a ValueError.

But for our program, it may be better to raise InvalidAgeException instead.

Question: If we raise InvalidAgeException, how can we avoid losing the original ValueError?

Solution: Exception Chaining

Python supports exception chaining:

raise NewException(...) from old_exception

This tells Python:

  • raise the new exception
  • and keep the original exception attached to it

When you do this, Python stores the original exception in the attribute __cause__:

new_exception.__cause__

Lets refactor Person to:

  • convert age text using int(...)
  • raise InvalidAgeException for our program
  • chain the original ValueError so we keep the debugging details
class Person:
    def __init__(self, name, age_text):
        self.name = name

        # Step 1: Convert to int (this can fail with ValueError)
        try:
            age = int(age_text)
        except ValueError as e:
            # Step 2: Raise a domain-specific exception (InvalidAgeException) 
            # and keep the original (ValueError binded to the variable e)
            # through exception chaining.
            raise InvalidAgeException(age_text) from e
        # Enforce the age rule (no low-level cause here - it's our rule)
        if not (0 <= age <= 120):
            raise InvalidAgeException(age)

        self.age = age
try:
    turing = Person("Alan Turing", "twelve")
except InvalidAgeException as e:
    print("Caught:", e)
    print("Cause:", repr(e.__cause__))
Output
Caught: InvalidAgeException(twelve): Valid ages must be between 0 and 120
Cause: ValueError("invalid literal for int() with base 10: 'twelve'")
try:
    turing = Person("Alan Turing", -1)
except InvalidAgeException as e:
    print("Caught:", e)
    print("Cause:", repr(e.__cause__))  # will be None (not chained)
Output
Caught: InvalidAgeException(-1): Valid ages must be between 0 and 120
Cause: None

Final Remarks

Key Takeaways

  • Exceptions are Python’s way of signaling problems at run time.
  • A traceback shows where an exception occurred and how execution arrived there.
  • Exception handling enables a controlled transfer of responsibility:
    • low-level code detects problems
    • higher-level code decides how to respond
  • Custom exceptions let us express domain-specific rules clearly.
  • Exception chaining (raise ... from ...) allows us to:
    • present meaningful, high-level errors
    • while preserving low-level details for debugging via __cause__

Big idea:
Good exception design is not just about handling errors, it is about communicating intent and responsibility in your programs.
