Lecture 6 · Part 1

Polymorphism & Duck Typing

  • Motivation
  • Polymorphism
  • Dynamic Typing + Late Binding
  • Duck Typing

Motivation

The Problem We Want to Solve

As programs grow, we often want to:

  • Perform the same operation on different kinds of data
  • Avoid rewriting the same logic for every new data type
  • Write code that is flexible and reusable

Real-World Analogy

Think about the action “open”:

  • Open a door
  • Open a bottle
  • Open a file

The action is the same, but the implementation depends on the object.

Programming Analogy

In code, we often want:

  • One function name
  • One loop
  • One algorithm

but different behavior depending on the object being used,

  • this idea is called polymorphism.

How This Looks in C

In C, types are fixed and explicit:

  • Every function specifies exact parameter types
  • The compiler enforces type correctness

This often leads to:

  • Multiple functions that do very similar things
  • Logic duplicated across types

Example

In C, you might see:

  • print_int(...)
  • print_double(...)
  • print_string(...)

Each function:

  • Does roughly the same job
  • But must be written separately for each type

The Core Question

How can we write one piece of code that works for many kinds of data?

Different languages answer this question differently:

  • How C answers the question

    • Use explicit types, multiple functions, or low-level mechanisms (void *, function pointers)
    • Polymorphism must be built manually by the programmer

  • How Python answers the question

    • Use runtime behavior instead of declared types
    • Allow functions to operate on any object that supports the required operations (known as duck typing)

Why This Matters in Python

Python takes a different approach than C:

  • Types are checked at runtime
  • Functions focus on behavior, not declared types
  • Code can be written to work with any object that supports the needed operations

Polymorphism is a natural result of this design.

Polymorphism

What Does “Polymorphism” Mean?

Poly = many
morph = forms

Polymorphism means:

  • The same operation (function call / method call) can work in many forms
  • The behavior can vary depending on the object involved

The Big Idea

“Write code once — use it with many kinds of objects.”

Polymorphism is about reusing algorithms without rewriting them for each type.

Polymorphism Is Not “A Python Feature”

Polymorphism is a general programming idea that shows up in many languages.

Different languages implement it differently.

Common Ways Languages Support Polymorphism

  1. Overloading (same function name, different parameter types)
    • Chosen at compile time (common in C++ / Java)
  2. Overriding (subclass changes a method’s behavior)
    • Chosen at runtime (common in Object Oriented languages)
  3. Interface-based polymorphism
    • “This object promises to provide these methods”
  4. Duck typing (Python’s usual approach)
    • “If it supports the operations we need, we use it”

Note: Python can implement options 2, 3 and 4. However, we will only be focusing on options 2 and 4:

  • Overriding (OOP / inheritance)
    • A subclass provides a different version of a method
    • Same method name, different behavior
  • Duck typing (Python’s common approach)
    • No special relationship required between classes
    • If an object supports the operations we need, we use it
# OVERRIDING (inheritance-based polymorphism)

class Animal:
    def speak(self):
        return "..."

class Dog(Animal):
    def speak(self):
        return "woof"

class Cat(Animal):
    def speak(self):
        return "meow"

def make_it_speak(animal):
    # Same call: animal.speak()
    print(animal.speak())

for animal in [Dog(), Cat()]:
    make_it_speak(animal)
Output
woof
meow
# DUCK TYPING (behavior-based polymorphism)

class DatabaseLogger:
    def log(self, message):
        print(f"[DB] {message}")

class FileLogger:
    def log(self, message):
        print(f"[FILE] {message}")

def audit(logger, message):
    # Works with any object that has a .log() method
    logger.log(message)

audit(DatabaseLogger(), "User signed in")
audit(FileLogger(), "User signed in")
Output
[DB] User signed in
[FILE] User signed in

Questions

  • In the first example, what do Dog and Cat have in common?
  • In the second example, do DatabaseLogger and FileLogger need to share a parent class?
  • What matters most in duck typing: the object’s type, or what it can do?

Key Contrast

  • Overriding: “same method name, different classes (often related by inheritance)”
  • Duck typing: “same operation, unrelated types are fine as long as they support it”

What You Should Remember

  • Polymorphism = same call, different behavior
  • In Python, polymorphism often happens through duck typing
  • Inheritance is one way to get polymorphism, but not the only way

Dynamic Typing + Late Binding

Dynamic Typing

In Python:

  • Variables do not have fixed types
  • Objects have types, but variables can point to any object over time

Example

So the same variable name could refer to:

  • an integer now
  • a string later
  • a list later
# DYNAMIC TYPING (variables can refer to different kinds of objects)

x = 10
print(x, type(x))

x = "hello"
print(x, type(x))

x = [1, 2, 3]
print(x, type(x))
Output
10 <class 'int'>
hello <class 'str'>
[1, 2, 3] <class 'list'>

This is type system is referred to as dynamic typing.

C Analogy: Variables Have Fixed Types

In contrast, in the language C, the variable has a fixed type determined at compile time.

That means this kind of “reassignment across types” is not allowed:

/* C (fixed types) */

int x = 10;
x = "hello";     // ERROR: assigning a string (char*) to an int

int* p = &x;
p = "hello";     // ERROR: assigning char* to int*

Why Dynamic Typing Matters for Polymorphism

Because functions don’t require a declared type:

  • A function can accept many kinds of objects
  • As long as the function only uses operations those objects support

This makes “generic” code feel natural in Python.

def summarize(x):
    """
    Return a short summary of x.
    This function works with any object that:
      - can be converted to a string (str(x))
      - has a length (len(x))
    """
    return f"type={type(x).__name__}, len={len(x)}, preview={str(x)[:25]!r}"


print(summarize("hello world"))             # string
print(summarize([10, 20, 30, 40]))          # list
print(summarize({"a": 1, "b": 2, "c": 3}))  # dict
Output
type=str, len=11, preview='hello world'
type=list, len=4, preview='[10, 20, 30, 40]'
type=dict, len=3, preview="{'a': 1, 'b': 2, 'c': 3}"

Remarks:

  • We never said: “x must be a string” or “x must be a list”
  • We only used:
    • len(x) (works for many built-in types)
    • str(x) (works for basically everything)

This is polymorphism driven by behavior.

Late Binding

When you call a method like:

`obj.speak()`

Python does not decide what .speak() means until runtime.

It looks at the actual object right now and then finds the method to run.

Why Late Binding Matters for Polymorphism

Polymorphism needs:

  • the same call
  • different behavior

Late binding makes that happen naturally in Python:

  • override methods in subclasses
  • or rely on duck typing (same method name across unrelated classes)
# LATE BINDING (the method is chosen at runtime)

class Dog:
    def speak(self):
        return "woof"

class Person:
    def speak(self):
        return "hello"

def say_it(obj):
    # Python decides what speak() is at runtime
    print(obj.speak())
say_it(Dog())     # woof
say_it(Person())  # hello
Output
woof
hello

Follow-up Questions

  1. In say_it(obj), where do we specify the type of obj?

We don’t. obj is untyped in the function signature; the function just assumes obj will support speak().

  1. What happens if we pass an object that does not have speak()?

You get a runtime error (an AttributeError) when Python tries to evaluate obj.speak().

say_it("Person")
Output
---------------------------------------------------------------------------

----> 1 say_it("Person")

---> 13     print(obj.speak())

AttributeError: 'str' object has no attribute 'speak'
  1. How does this differ from what you’re used to in C?

In C, parameter types are fixed at compile time, so the compiler enforces what you can pass. In Python, the check happens at runtime based on whether the object has the needed behavior.

Key Takeaway

Dynamic typing + late binding means:

  • Python code often cares more about behavior than declared type
  • Polymorphism is common and “built in” to the way Python runs code

Duck Typing

The “Duck Test”

“If it walks like a duck, swims like a duck and quacks like a duck then it’s a Duck!”

In programming terms:

  • If it has the right methods / supports the right operations we treat it as the right kind of thing.

Duck Typing Is How Polymorphism Usually Looks in Python

We often write functions that:

  • don’t check types up front
  • just use the methods they need
  • and rely on the object to provide that behavior

Example

We want a single function that can “send a notification”.

We don’t want to write:

  • send_email_notification(...)
  • send_sms_notification(...)
  • send_slack_notification(...)

Instead, we’ll write one function that assumes:

“If you can .send(message), you’re a notifier.”

class EmailNotifier:
    def send(self, message):
        print(f"[EMAIL] {message}")

class SMSNotifier:
    def send(self, message):
        print(f"[SMS] {message}")

class ConsoleNotifier:
    def send(self, message):
        print(f"[CONSOLE] {message}")


def notify_all(notifiers, message):
    # Duck typing: no type checks here.
    # We rely on each object supporting .send(message).
    for n in notifiers:
        n.send(message)
notifiers = [EmailNotifier(), SMSNotifier(), ConsoleNotifier()]
notify_all(notifiers, "This weeks topic is Polymorphism and Duck Typing")
Output
[EMAIL] This weeks topic is Polymorphism and Duck Typing
[SMS] This weeks topic is Polymorphism and Duck Typing
[CONSOLE] This weeks topic is Polymorphism and Duck Typing
# Failure case: object doesn't provide the expected behavior

class BrokenNotifier:
    def send_message(self, message):
        print(f"[BROKEN] {message}")
notifiers = [EmailNotifier(), BrokenNotifier()]
notify_all(notifiers, "Reminder: assignment due Friday.")
Output
[EMAIL] Reminder: assignment due Friday.

Remarks:

  • notify_all never checks types (no isinstance)
  • It uses the behavior it needs: .send(message)
  • Any class can “plug in” as long as it provides the method

Follow-up Questions:

  1. What exactly is the informal contract for objects passed to notify_all?
  • notifiers must be an iterable collection of objects,
    • and each object must provide a callable method:send(message),
    • where message is the value passed into notify_all (typically a string).
  1. What error will happen in the failure case, and on what line?
  • An AttributeError occurs when the loop reaches BrokenNotifier(), because it has no send method.
    • It happens on the line inside notify_all: n.send(message)

What Duck Typing Is NOT

Duck typing is not:

  • “anything goes”
  • “types don’t matter”
  • “write messy code”

Duck typing still has rules:

  • the rule is behavior
  • the rule is operations needed by the code

Good Habits for Programming Functions

Before writing a function, ask:

  • What methods/operations must the input support?

Example requirement statements:

  • “must have .read()”
  • “must be iterable” (supports looping)
  • “must support len()”
  • “must support indexing x[i]”
# Ignoring input behaviour (bad habits)
# Problem: if num is an int, you can't loop over it (ints are not iterable).

def find_largest_digit(num):
    largest = 0
    for digit in num:  # TypeError if num is an int
        if digit > largest:
            largest = digit
    return largest

# Focusing on input behaviour (good habits)
# Informal contract:
#   - We need to loop over the digits, so we convert num to a string.
#   - We compare digits as characters, then convert back to int at the end.

def find_largest_digit(num):
    largest = "0"                 # keep as a string so digit comparison works consistently
    for digit in str(num):        # convert to string so we can loop over the digits
        if digit > largest:
            largest = digit
    return int(largest)           # convert the largest digit back to an int

Output
7

Key Takeaway

Duck typing = “programming by capability”

  • Focus on behavior
  • Avoid hard-coding types
  • Write flexible, reusable code
