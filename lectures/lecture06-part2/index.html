Duck Typing in Practice

Duck Typing Through Protocols

Duck typing applies to common “protocols” (informal rules about behavior), like:

  • Method calls: obj.draw(), obj.send(msg)
  • Built-in functions: len(x), sorted(x), sum(x)
  • Operators: x + y, x in y, x[i]
  • Iterables / iteration: for item in x:
    • If something works in a for loop, it’s following the iteration protocol

In all cases, Python is relying on supported operations, not declared types.

Examples of Common Protocols

# 1) METHOD CALLS: obj.draw()

class Circle:
    def draw(self):
        print("Drawing a circle")

class Triangle:
    def draw(self):
        print("Drawing a triangle")

def render(shape):
    # Works with anything that has .draw()
    shape.draw()

render(Circle())
render(Triangle())
Output
Drawing a circle
Drawing a triangle
# 2) BUILT-IN FUNCTIONS: len(x), sorted(x), sum(x)

# has length
print(len("hello"))          # 5
print(len([10, 20, 30]))     # 3

# can be sorted
print(sorted([3, 1, 2]))     # [1, 2, 3]
print(sorted("python"))      # ['h', 'n', 'o', 'p', 't', 'y']

# can be summed
print(sum([1, 2, 3, 4]))     # 10
print(sum((5, 5, 5)))        # 15

# supports addition
print("py" + "thon")         # 'python'
print([1, 2] + [3, 4])       # [1, 2, 3, 4]

# supports membership check; 'in'
print("a" in "cat")          # True
print(2 in [1, 2, 3])        # True

# supports indexing
print("hello"[1])            # 'e'

# If it works in a for-loop, it's following the iteration protocol.

    print(ch)

for num in [10, 20, 30]:
    print(num)

What to Notice

  • Same syntax works across different types because Python checks for supported behavior at runtime.
  • Each category above corresponds to “what operations does this object support?”
    • .draw() method exists?
    • has a length?
    • can be sorted / summed?
    • supports +, in, indexing?
    • supports iteration for a for loop?

Duck Typing vs Inheritance

Two Ways to Get “Same Call, Different Behavior”

  1. Inheritance-based polymorphism

    • Classes share a common parent
    • Child classes override methods

  2. Duck typing (behavior-based)

    • Classes do not need a common parent
    • As long as they support the same operations, they work

Inheritance-Based Polymorphism

When inheritance is used, we often have:

  • A base class that defines a common method name
  • Subclasses that override that method

This is useful when:

  • there is a true “is-a” relationship
  • subclasses share data and shared default behavior
# INHERITANCE EXAMPLE: shared base class + overriding
# There is an "is-a" relationship

class Animal:
    def speak(self):
        raise NotImplementedError("Subclasses must override speak()")

class Dog(Animal):
    def speak(self):
        return "woof"

class Cat(Animal):
    def speak(self):
        return "meow"

def make_it_speak(animal):
    print(animal.speak())

make_it_speak(Dog())
make_it_speak(Cat())
Output
woof
meow

Duck Typing Based Polymorphism

With duck typing, we often have:

  • unrelated classes
  • a shared method name (or shared set of operations)
  • functions written to use those operations

This is useful when:

  • types are unrelated
    • they share a “has-a”/“can-do” relationship instead of “is-a” relationship
  • you want plug-and-play behavior
  • you don’t control the class definitions (library code)
# DUCK TYPING POLYMORPHISM EXAMPLE: no shared base class required
# There is a common "can-do" relationship

class Dog:
    def speak(self):
        return "woof"

class Robot:
    def speak(self):
        return "beep"

def make_it_speak(thing):
    # Works with any object that has speak()
    print(thing.speak())

make_it_speak(Dog())
make_it_speak(Robot())
Output
woof
beep

Key Contrast

Inheritance-Based Polymorphism:

  • “You are part of this family (base class)”
  • Relationship is explicit in the class design (“is-a” relationship)

Duck Typing Based Polymorphism:

  • “You can do this job (provide this behavior)”
  • Relationship is implicit in the methods/operations (“has-a”/“can-do” relationship)

Common Mistake

Using inheritance when you only need shared behavior:

  • Inheritance is not for “I want to reuse a function”
  • Inheritance is best when objects share a meaningful category and shared structure

Duck typing is often simpler when you only need a capability.

Example:

We want one function that computes a total cost for different “things”.

Common instinct:

  • “Make them all inherit from a common base class.”

But often the better question is:

  • Are these objects truly the same kind of thing (is-a)?
  • Or do they just share a capability (can-do)?

Here the capability is:

  • “You can produce a number when asked for your total.”
# BAD FIT FOR INHERITANCE: forcing unrelated objects into one family tree

class Billable:
    def total(self):
        raise NotImplementedError("Subclasses must implement total()")


class ShoppingCart(Billable):
    def __init__(self, prices):
        self.prices = prices

    def total(self):
        return sum(self.prices)


class Invoice(Billable):
    def __init__(self, line_items):
        self.line_items = line_items  # list of (description, cost)

    def total(self):
        return sum(cost for desc, cost in self.line_items)


class Subscription(Billable):
    def __init__(self, monthly_cost, months):
        self.monthly_cost = monthly_cost
        self.months = months

    def total(self):
        return self.monthly_cost * self.months
def print_totals(billables):
    for b in billables:
        print(b.total())

items = [
    ShoppingCart([12.99, 4.50, 6.25]),
    Invoice([("setup", 50), ("support", 20)]),
    Subscription(9.99, 3)
]

print_totals(items)
Output
23.740000000000002
70
29.97

Why This Is a “Bad Fit”

  • ShoppingCart, Invoice, and Subscription aren’t really the same “kind” of object.
  • The base class doesn’t provide shared data or shared default behavior.
  • The only thing they share is one method name: .total().

Inheritance works, but it’s not pulling its weight.

Better Fit: Duck Typing

We can drop the base class entirely. The function only needs one capability:

  • each object must provide total() -> number
# BETTER: duck typing (no required base class)

class ShoppingCart:
    def __init__(self, prices):
        self.prices = prices

    def total(self):
        return sum(self.prices)


class Invoice:
    def __init__(self, line_items):
        self.line_items = line_items

    def total(self):
        return sum(cost for desc, cost in self.line_items)


class Subscription:
    def __init__(self, monthly_cost, months):
        self.monthly_cost = monthly_cost
        self.months = months

    def total(self):
        return self.monthly_cost * self.months
def print_totals(things):
    # Duck typing: any object with total() works
    for t in things:
        print(t.total())


items = [
    ShoppingCart([12.99, 4.50, 6.25]),
    Invoice([("setup", 50), ("support", 20)]),
    Subscription(9.99, 3)
]

print_totals(items)
Output
23.740000000000002
70
29.97

Class Discussion:

  1. What is the informal contract for objects passed to print_totals?

    def print_totals(things):
   # Duck typing: any object with total() works
   for t in things:
       print(t.total())
  • things must be an iterable collection of objects, and each object must provide a callable method: total()
    • total() should return a number (e.g., int or float) that can be printed.
  1. If you add a new class Donation with a .total() method, do you need to change print_totals?
  • No. As long as Donation implements total() and returns a number, it will work automatically.
  1. When would inheritance actually be a better choice than duck typing here?
  • When there is a true is-a relationship and shared structure/behavior, for example:
    • All objects share common attributes (e.g., customer_id, date, tax_rate)
    • The base class can provide useful shared default methods (e.g., apply_tax(), format_receipt())
    • You want to enforce a consistent design across a large codebase (a clear “family” of related types)

Takeaway

  • Inheritance is one tool for polymorphism, but it’s not required.
  • Duck typing often leads to simpler, more flexible designs in Python.
  • A good question to ask: “Is this an is-a relationship, or just a has-a/can-do relationship?”
    • If is-a relationship then use inheritance-baed polymorphism
    • If has-a/can-do relationship then use duck typing

Benefits

Why Duck Typing Is Useful in Python

Duck typing is useful because it helps you write code that is:

  • Reusable

    • One function can work with many different kinds of objects

  • Flexible

    • New classes can “plug in” later without changing existing code

  • Simple

    • You often don’t need extra inheritance hierarchies
    • Fewer “framework” classes just to make things fit

  • Good for teamwork / libraries

    • You can use objects from libraries you didn’t write
    • As long as they support the operations your code expects

Duck typing encourages:

  • “Write functions in terms of what you need”
  • not “Write functions in terms of what type it is”
# "plug-in" behavior without changing the function

class EmailNotifier:
    def send(self, message):
        print(f"[EMAIL] {message}")

class SMSNotifier:
    def send(self, message):
        print(f"[SMS] {message}")

def notify_all(notifiers, message):
    for n in notifiers:
        n.send(message)   # duck typing: only requires .send()

notifiers = [EmailNotifier(), SMSNotifier()]
notify_all(notifiers, "Remainder: Midterm during week 9.")
Output
[EMAIL] Remainder: Midterm during week 9.
[SMS] Remainder: Midterm during week 9.
# Later, we add a new notifier type without changing notify_all:

class ConsoleNotifier:
    def send(self, message):
        print(f"[CONSOLE] {message}")

notifiers.append(ConsoleNotifier())
notify_all(notifiers, "Assignment 2 posted.")
Output
[EMAIL] Assignment 2 posted.
[SMS] Assignment 2 posted.
[CONSOLE] Assignment 2 posted.

Remarks:

  • notifiers must be iterable, and each element must provide a callable method: send(message)

  • When we added ConsoleNotifier:

    • We did not have to change notify_all at all (and we didn’t need to change EmailNotifier or SMSNotifier either).
    • We only added a new class and appended an instance to the notifiers list.

  • This useful as programs grows because:

    • You can add new behaviors by adding new classes (plug-ins) without editing existing logic.
    • Less duplicated code, fewer “if/else type checks”, and fewer places to break things when extending the program.

Risks / Trade-offs

The Trade-Off

Duck typing gives flexibility, but it moves some checks from:

  • compile time (before the program runs) to:
  • runtime (while the program runs)

So mistakes can show up later.

Common Risks

  • Runtime errors

    • If an object is missing a required method, you get an error when that line runs

  • Typos in method names

    • A misspelled method name won’t be caught until the code executes

  • Unclear expectations

    • Without a clear “informal contract”, it may not be obvious what a function expects

  • Harder debugging in larger programs

    • Problems can appear far away from where the wrong object was created/passed in

Example of a Typical Duck Typing Failure

A function assumes a capability:

  • “must have .send(message)”

If the object doesn’t match that expectation, you get a runtime error.

# typo / missing method leads to runtime error

class EmailNotifier:
    def send(self, message):
        print(f"[EMAIL] {message}")

class BrokenNotifier:
    #  Accidentally used a different method name
    def send_message(self, message):
        print(f"[BROKEN] {message}")

def notify_all(notifiers, message):
    for n in notifiers:
        n.send(message)   # assumes .send exists

notifiers = [EmailNotifier(), BrokenNotifier()]
notify_all(notifiers, "Quiz today.")

Designing with Duck Typing (Practical Habits)

The Design Mindset

When designing functions that use duck typing, think in terms of:

“What does this object need to be able to do?”

not:

“What type is this object?”

Habit 1: State the Required Behavior Clearly

Before writing code, ask:

  • What methods must the object provide?
  • What operations will I use?

Even if Python doesn’t enforce it, you should know the answer.

Habit 2: Write Functions Around Capabilities

Good duck-typed functions:

  • are small
  • focus on one job
  • rely on a small number of operations

The fewer operations you require, the more flexible your function is.

Habit 3: Avoid Type Checks

Instead of writing:

    if isinstance(x, Person):
        print(x.talk())

Writing code that just uses the needed behavior:

    print(x.talk())

Type checks (isinstance) usually mean:

  • your function is doing too many things
  • or your design is too rigid

Habit 4: Use Clear, Descriptive Method Names

Duck typing depends on shared expectations.

Clear method names:

  • make contracts easier to understand
  • reduce accidental mismatches

Example:

  • send(message) is clearer than do_it(x)

Habit 5: Fail Clearly (Not Silently)

When duck typing fails:

  • you want the error to happen quickly
  • and as close as possible to the source

This makes bugs easier to find and fix.

    try:
        x.talk()
    except AttributeError as e:
        print(f"Error: {type(e)__name__} ({e})")

Key Takeaway

Designing with duck typing is a skill:

  • focus on behavior
  • keep functions small
  • make expectations obvious
# DESIGN HABIT EXAMPLE: small function, clear capability

# GOOD: duck typing (behavior over concrete type)
def print_combined(pairs):
    """
    Informal contract:
      - pairs is iterable of (a, b)
      - a + b works
    """
    for a, b in pairs:
      try:
        print(a + b)
      except TypeError:
        print("Skipping: '+' failed for:", (a, b))


print_combined([("hello ", "world"), (1, 2), ([1, 2], [3]), ("three", 2)])
Output
hello world
3
[1, 2, 3]
Skipping: '+' failed for: ('three', 2)
# WHAT NOT TO DO: rigid design using type checks

# BAD HABIT: "defensive" checks (contrived and brittle)
def print_combined_checked(pairs):
    """
    Informal contract (attempted):
      - pairs is iterable of (a, b)
      - a and b support +
    This version tries to *prove* the contract with checks first.
    """
    for pair in pairs:
        # Over-check shape
        if not isinstance(pair, (list, tuple)) or len(pair) != 2:
            print("Skipping: not a 2-item pair:", pair)
            continue

        a, b = pair

        # Over-check type families (brittle: misses lots of valid 'addable' types)
        if isinstance(a, int) and isinstance(b, int):
            print(a + b)
        elif isinstance(a, str) and isinstance(b, str):
            print(a + b)
        elif isinstance(a, list) and isinstance(b, list):
            print(a + b)
        else:
            # "Hasattr" doesn't really prove '+' works, but people try it anyway
            if hasattr(a, "__add__"):
                try:
                    print(a + b)
                except TypeError:
                    print("Skipping: '+' failed for:", (a, b))
            else:
                print("Skipping: no __add__:", (a, b))


print_combined_checked([("hello ", "world"), (1, 2), ([1, 2], [3]), ("three", 2)])
Output
hello world
3
[1, 2, 3]
Skipping: '+' failed for: ('three', 2)

LBYL vs EAFP

(Pythonic Coding Style)

Two Design Styles You’ll See in Python

When writing code that might fail, there are two common styles:

  • LBYL — Look Before You Leap
  • EAFP — Easier to Ask Forgiveness than Permission

Both are valid, but Python strongly leans toward EAFP.

LBYL: Look Before You Leap

LBYL means:

  • Check conditions before doing the operation
  • Try to prevent errors by guarding every step

General shape:

  • “If this looks safe, then do it”
# LBYL STYLE

class Text:
    def __init__(self, text):
        self._text = text

class Source(Text):
    def read(self):
        return self._text

def read_text_lbyl(source):
    # LBYL: check first, then use
    if hasattr(source, "read"): # Checks if source has attribute "read"
        if callable(source.read): # Checks if source.read is callable, i.e. source.read is a method
            return source.read()
    else:
        raise ArithmeticError("Object does not support read()")
read_text_lbyl(Source('Will program for coffee'))
Output
'Will program for coffee'
read_text_lbyl(Text('Will program for coffee'))
Output
---------------------------------------------------------------------------
ArithmeticError                           Traceback (most recent call last)
Cell In[19], line 1
----> 1 read_text_lbyl(Text('Will program for coffee'))

Cell In[17], line 17, in read_text_lbyl(source)
     15         return source.read()
     16 else:
---> 17     raise ArithmeticError("Object does not support read()")

ArithmeticError: Object does not support read()

EAFP: Easier to Ask Forgiveness than Permission

EAFP means:

  • Perform the operation directly
  • Handle errors if they occur

General shape:

  • “Try it, and deal with failure if it happens”
def read_text_eafp(source):
    # EAFP: try the operation, handle the failure
    try:
        return source.read()
    except AttributeError as e:
        #print("Object does not support read()")
        print(f"Error: {type(e).__name__} ({e})")
read_text_eafp(Source('Will program for coffee'))
Output
'Will program for coffee'
read_text_eafp(Text('Will program for coffee'))
Output
Error: AttributeError ('Text' object has no attribute 'read')

Why This Matters for Duck Typing

Duck typing says:

  • Focus on behavior
  • Don’t rely on explicit type checks

EAFP fits naturally with duck typing because:

  • You try the behavior you need
  • You handle failure if the object doesn’t support it

LBYL often pushes you back toward:

  • type checks
  • rigid assumptions
  • brittle code (everything appears to work, but unexpected failures can occur later)

Another Example

#person = {'name': 'Alan', 'age': 23, 'job': 'Computer Scientist'}
person = {'name': 'Alan', 'age': 23}
# LBYL (Non-Pythonic)
# Perform checks to see if person dictionary has keys 'name', 'age', and 'job'
if 'name' in person and 'age' in person and 'job' in person:
    print("I'm {name}. I'm {age} years old and I am a {job}".format(**person))
else:
    print('Missing some keys')
Output
Missing some keys
# EAFP (Pythonic)
# We don't perform any checks, we simply try
try:
    print("I'm {name}. I'm {age} years old and I am a {job}".format(**person))
except KeyError as e:
    print(f"Missing {e} key")
Output
Missing 'job' key

Wrap-up

Wrap-up: What We Learned

  • Polymorphism means: same operation, different behavior
  • In Python, polymorphism commonly appears through duck typing when there is a “has-a/can-do” relationship
  • Inheritance is optional, should only be applied when there is an “is-a” relationship
  • Duck typing focuses on what an object can do, not what type it is

The Key Design Question

When writing a function, always ask:

“What does my input need to be able to do?”

Examples:

  • “must support len(x)”
  • “must be iterable”
  • “must have .send(message)”

These are informal contracts.

The Trade-off

Duck typing gives flexibility, but:

  • mistakes are caught at runtime
  • errors can be unclear if expectations aren’t stated
