Hashing

Motivation

So far we’ve improved search by using information about item ordering:

  • Binary search –> O(logn)O(\log n)

Can we do even better?

Hashing builds a data structure that can be searched in O(1)O(1) time — a constant time search.

The idea: know exactly where an item should be before you even look.

The Hash Table

A hash table is a collection of items stored to make them easy to find later.

  • Each position is called a slot, named by an integer starting at 0
  • Initially every slot is empty (None)

Example: a hash table of size m=11m = 11 (slots 0–10):

Remainder Method

To fill our hash table, lets define a hash function hh, that maps each item to a slot number (0 to m−1m-1):

  • h(item) = item % table_size (Remainder method)

Example

For items {54, 26, 93, 17, 77, 31} with table size 11:

Item Hash Value (Item % 11)
54 10
26 4
93 5
17 6
77 0
31 9

Each item goes into its designated slot:

O(1)O(1) Search!

To search for an item:

  1. Compute its hash value
  2. Check that slot in the table

Example

Lets check if the following items are in our hash table:

  • item = 93 –> hash value = h(93)=93%11=5h(93) = 93 \% 11 = 5. Check slot 5 –> 93 ✔
  • item = 18 –> hash value = h(18)=18%11=6h(18) = 18\%11 = 6. Check slot 7 –> None ✘

Only one comparison needed –> O(1)O(1)

…but there’s a catch.

Collisions

What if two items hash to the same slot?

  • 77 % 11 == 0 ✓
  • 44 % 11 == 0 — but slot 0 is taken!

This is called a collision (or clash).

We need strategies to handle collisions — more on this shortly.

Hash Functions

A hash function that maps every item to a unique slot is a perfect hash function.

Perfect hash functions are rarely achievable for arbitrary data — but we can get close.

Goals for a good hash function:

  • Minimizes collisions
  • Easy to compute
  • Evenly distributes items across the table

Folding Method

  1. Divide the item into equal-size pieces
  2. Add the pieces together
  3. Apply remainder method

Example: phone number 436-555-4601

  • Split into groups of 2: 43, 65, 55, 46, 01
  • Sum: 43 + 65 + 55 + 46 + 01 = 210
  • 210 % 11 = 1 –> hashes to slot 1

Variant — reverse every other piece:

  • 43 + 56 + 55 + 64 + 01 = 219
  • 219 % 11 = 10 –> hashes to slot 10

Mid-Square Method

  1. Square the item
  2. Extract middle digits
  3. Apply remainder method

Example: item = 44

  • 442=193644^2 = 1936
  • Middle two digits: 93
  • 93%11=593 \% 11 = 5 –> slot 5

Comparison of methods:

Item Remainder Mid-Square
54 10 3
26 4 7
93 5 9
17 6 8
77 0 4
31 9 6

Hashing Strings

Ordinal Values

Every character has a numeric ordinal value based on its position in the Unicode standard (a superset of ASCII):

  • ord(char) returns the integer ordinal of a single character:

    • ord('A') = 65,
    • ord('a') = 97,
    • ord('0') = 48

Hashing Strings

Strings can be hashed using their ordinal values:

>>> ord('c')  # 99
>>> ord('a')  # 97
>>> ord('t')  # 116

def hash_string(astring, tablesize):
    total = 0
    for pos in range(len(astring)):
        total = total + ord(astring[pos])
    return total % tablesize

print(hash_string('cat', 11))
print(hash_string('act', 11))  # anagram — same hash!
Output
4
4

Collision Resolution

When two items hash to the same slot, we need a systematic method to place the second item.

Open addressing: find the next open slot in the hash table.

The simplest strategy is linear probing — move sequentially through slots until an empty one is found.

Linear Probing

Recall our hash table with the six items: {54, 26, 93, 17, 77, 31}

Lets say we want to add the additional items: {44, 55, 20}

  • 44 hashes to slot 0 (taken by 77) –> placed in slot 1
  • 55 hashes to slot 0 (taken) –> slot 1 (taken) –> slot 2
  • 20 hashes to slot 9 (taken by 31) –> slot 10 –> slot 0 –> slot 1 –> slot 2 –> slot 3

The Clustering Problem

Linear probing causes clustering – items pile up around busy slots.

This makes future insertions and lookups slower as the cluster grows.

Rehashing: Skipping to Reduce Clustering

Instead of checking the next slot, skip multiple slots:

rehash(pos) = (pos + skip) % table_size

“Plus 3” probe: after a collision, jump 3 slots at a time:

  • 44 hashes to slot 0 (taken by 77) –> placed in slot 3 =(0+3)%11= (0+3)\%11
  • 55 hashes to slot 0 (taken) –> slot 3 –> slot 6 –> slot 9 –> slot 1
  • 20 hashes to slot 9 (taken by 31) –> slot 1 –> slot 4 –> slot 7

Remark:

The skip value and table size must be co-prime (gcd(skip value,table size)=1\mathrm{gcd}(\text{skip value}, \text{table size}) = 1) so all slots are eventually visited.

This is why table sizes are often prime numbers.

Quadratic Probing

Instead of a fixed skip, use successive perfect squares as offsets:

If first hash value is hh, successive probes go to: h+12,h+22,h+32,h+42,…h+1^2,\quad h+2^2,\quad h+3^2,\quad h+4^2, \ldots

rehash(pos,i)=(h+i2)%table size\mathrm{rehash}(\mathrm{pos}, i) = (h + i^2)~ \% ~\text{table size}

  • 44 hashes to slot 0 (taken by 77) –> placed in slot 1
  • 55 hashes to slot 0 (taken) –> slot 1 –> slot 4 –> slot 9 –> slot 5 –> slot 3
  • 20 hashes to slot 9 (taken by 31) –> slot 10 –> slot 2 –> slot 7

Chaining

An alternative to open addressing — allow each slot to hold a collection of items.

When a collision occurs, the item is added to the chain at that slot:

  • Advantage: no need to find another slot
  • Disadvantage: as chains grow, search within a slot gets slower

Analysis of Hashing

Best case: O(1)O(1) — but collisions make the real average more complex.

The key variable is the load factor λ=itemstable size\lambda = \dfrac{\text{items}}{\text{table size}}:

  • Small λ\lambda → fewer collisions → items are where they belong
  • Large λ\lambda → more collisions → harder to find empty slots

Summary

Concept Key Idea
Hash table Collection of slots indexed by integer names
Hash function Maps an item to a slot — ideally unique
Collision Two items map to the same slot
Linear probing Scan sequentially for the next open slot
Quadratic probing Skip by successive squares to reduce clustering
Chaining Each slot holds a list of items
Load factor λ\lambda Items / table size — lower is better

Best case: O(1)O(1) search — achieved when load is low and collisions are rare.
